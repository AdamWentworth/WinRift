# Read-Model Coverage Audit

This audit maps the app's visible pages to the backend data path they rely on. The goal is simple: stored analytics pages should feel instant, remain usable after old raw payloads are pruned, and avoid request-time aggregation over bulky tables.

Status meanings:

- Green: public path is summary-backed, cached, or static enough for the current MVP.
- Amber: working, but still depends on normalized row scans, fallback scans, or request fan-out that could become slow as data grows.
- Red: should not be considered production-ready without a read model.

## Endpoint Notes

### `/api/analytics/champion-page`

This endpoint is correctly bundled and has both in-memory and ClickHouse-backed response caching. That is the right public shape. The remaining issue is what happens during a cold cache:

- Good: `champion_skill_analytics`, `champion_ban_analytics`, `champion_build_variant_analytics`, item-slot analytics, and starting-loadout analytics already avoid raw JSON scans.
- Good: bundle caching means repeated clicks on the same champion/role/patch become cheap.
- Needs work: champion summary, matchups, rune signatures, and spell signatures still read from `participant_matchups`/`participant_performance` through `championGuideBaseSQL`.
- Needs work: item paths intentionally combine retained normalized rows with `patch_build_metrics`, which is acceptable for current patches but should become summary-only for archived patches.

Recommended read models:

- `champion_matchup_analytics`: champion, role, opponent champion, patch, rank bucket, wins, games.
- `champion_signature_analytics`: champion, role, patch, rank bucket, signature type, signature, wins, games.
- `champion_performance_summary_analytics`: champion, role, patch, rank bucket, performance sums, wins, games.
- `team_kill_summary`: match/team kill totals used to calculate true kill participation without nested aggregate tricks.

### `/api/summoner/profile`

The page is mostly in good shape. The top-level overview and champion stats tabs are summary-backed. The two weak spots are intentionally user-specific:

- recent matches need match timestamp/duration and currently join `raw_matches`,
- build usage currently groups normalized participant rows.

Recommended read models:

- `summoner_recent_match_summary`: platform, PUUID, queue, match, patch, champion, role, win, KDA, timestamp, duration.
- `summoner_build_summary`: platform, PUUID, queue, champion, role, final/core/rune/spell signatures, wins, games, KDA sums.

These would make profiles independent of old raw match retention.

### `/api/analytics/build-advice`

The current design is policy-safe and usable: matchup rows stay contextual, sample labels are visible, and live mode only calls this endpoint when the user asks for build advice. The performance risk is that one advice response still assembles several slices:

- exact matchup item slots,
- champion-wide item slots,
- starting loadouts,
- build signatures,
- rune/spell/build variant context from the champion guide path.

Recommended read model:

- `build_advice_bundle_summary`: champion, role, opponent champion, patch, rank bucket, item context, starting loadouts, slot options, top builds, top runes, top spells, and sample diagnostics in one compact row or small row family.

This is the endpoint most likely to benefit from a true precomputed bundle.

## Raw-Pruning Safety

Current raw-pruning safety is partial:

- Patch coverage survives through `patch_snapshots`.
- Win-condition metrics survive through `patch_win_condition_metrics`.
- Build signatures survive through `patch_build_metrics`.
- Champion guide index/tier-list data survives through guide summary/scope/ban tables.
- Full champion guide pages still need more summary coverage for matchups, runes, spells, and some performance fields.
- Summoner recent matches/build usage still need dedicated summaries if we want older profile pages to stay rich after pruning.

For the MVP, pruning old bulky raw payloads is still acceptable as long as we accept that a few historical drill-down panels may be thinner than current/recent patch pages. Before showing patch-history features prominently, close the Amber items above.

## Recommended Order

1. Add `summoner_recent_match_summary` and `summoner_build_summary`.
2. Add champion matchup/rune/spell read models.
3. Add a team-kill summary and restore true kill participation to the fast guide path.
4. Add a build-advice bundle summary for live build mode.
5. Expand backend tests so each public endpoint has one test proving it uses the intended summary table.
