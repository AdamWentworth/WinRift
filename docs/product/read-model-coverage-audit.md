# Read-Model Coverage Audit

This audit maps the app's visible pages to the backend data path they rely on. The goal is simple: stored analytics pages should feel instant, remain usable after old raw payloads are pruned, and avoid request-time aggregation over bulky tables.

Status meanings:

- Green: public path is summary-backed, cached, or static enough for the current MVP.
- Amber: working, but still depends on normalized row scans, fallback scans, or request fan-out that could become slow as data grows.
- Red: should not be considered production-ready without a read model.

## Endpoint Notes

### `/api/analytics/champion-page`

This endpoint is correctly bundled and has both in-memory and ClickHouse-backed response caching. That is the right public shape. The remaining issue is what happens during a cold cache:

- Good: `champion_skill_analytics`, `champion_ban_analytics`, `champion_build_variant_analytics`, `champion_matchup_analytics`, `champion_signature_analytics`, `build_signature_analytics`, item-slot analytics, and starting-loadout analytics already avoid raw JSON scans.
- Good: selected champion summary now reuses `champion_guide_summary_analytics`, so the single-champion header no longer needs a separate participant aggregation on cold cache.
- Good: `team_kill_summary` feeds true kill participation into `champion_guide_summary_analytics`.
- Good: bundle caching means repeated clicks on the same champion/role/patch become cheap.
- Good: item paths now read build signatures from `build_signature_analytics` for current/recent patches and `patch_build_metrics` for archived patches before falling back to retained normalized rows in local/dev safety cases.
- Good: the worker now prewarms top champion/role bundles after champion-guide refreshes, and the cache key is canonicalized so query-param order does not create duplicate cache rows.

Recommended read models:

- Optional later: a true `build_advice_bundle_summary` JSON row per hot champion/opponent if we need CDN-like prewarming. The current MVP path is summary-backed enough that this is no longer the first bottleneck.

### `/api/summoner/profile`

The page is now summary-backed across its main tabs. The top-level overview, champion stats, recent matches, and build usage all prefer compact profile read models.

Fallback still exists for local/dev safety when summaries have not been populated yet:

- recent matches can fall back to `participants` plus `raw_matches`,
- build usage can fall back to direct `participants` aggregation.

Normal production reads should hit `summoner_recent_match_summary` and `summoner_build_summary`.

### `/api/analytics/build-advice`

The current design is policy-safe and usable: matchup rows stay contextual, sample labels are visible, and live mode only calls this endpoint when the user asks for build advice. One advice response still assembles several slices, but those slices now come from compact read models:

- exact matchup item slots,
- champion-wide item slots,
- starting loadouts,
- build signatures from `build_signature_analytics` or archived `patch_build_metrics`,
- rune/spell/build variant context from the champion guide path.

If this endpoint becomes hot under real traffic, the next step is response prewarming for popular champion/opponent pairs, not a request-time aggregation change.

## Raw-Pruning Safety

Current raw-pruning safety is partial:

- Patch coverage survives through `patch_snapshots`.
- Win-condition metrics survive through `patch_win_condition_metrics`.
- Build signatures survive through `patch_build_metrics`.
- Champion guide index/tier-list data survives through guide summary/scope/ban tables.
- Full champion guide pages have summary coverage for the current MVP panels. A future true bundle table can still help with public-scale traffic, but the app no longer depends on normalized row scans for common build signatures during normal production reads.
- Summoner recent matches/build usage survive through dedicated summaries for currently indexed profile data.

For the MVP, pruning old bulky raw payloads is still acceptable as long as we accept that a few historical drill-down panels may be thinner than current/recent patch pages. Before showing patch-history features prominently, close the Amber items above.

## Recommended Order

1. Add a champion role-rate summary if role discovery starts showing up in timing logs.
2. Expand hot-response prewarming to matchup-specific champion pages if deployed timings show frequent cold misses there.
3. Expand backend tests so each public endpoint has one test proving it uses the intended summary table.
